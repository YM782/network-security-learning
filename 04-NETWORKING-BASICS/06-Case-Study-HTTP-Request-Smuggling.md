# 04-06｜真實漏洞研究案例：HTTP Request Smuggling（HTTP 請求走私）

> 難度：初級至中級｜建議時間：120–150 分鐘｜先修：IP、TCP、HTTP Request/Response、反向代理
>
> 本課研究網站前端與後端對 HTTP 訊息邊界的理解不一致，如何形成安全漏洞。所有動手實驗只使用 PortSwigger Academy 或自己搭建的隔離環境。

## 一、先讀真實研究文章

[HTTP Desync Attacks: Request Smuggling Reborn — PortSwigger Research](https://portswigger.net/research/http-desync-attacks-request-smuggling-reborn)

這是 James Kettle 於 2019 年發表的真實研究文章，後續有更新。文章分析了多個真實網站和基礎設施中的 HTTP 去同步問題，並提出降低誤報和減少影響其他使用者風險的檢測思路。

**分類提醒：** HTTP Request Smuggling 是一整類協議解析差異漏洞，不是單一產品的一個 CVE。本課研究的是這個漏洞類別和研究方法；不會把它冒充成一個有固定 CVE 編號的個案。

## 二、先理解現代網站的架構

很多網站不是由一台伺服器直接處理所有請求，而是由多個元件串接：

    瀏覽器
       |
       v
    CDN / WAF
       |
       v
    Reverse Proxy
       |
       v
    Load Balancer
       |
       v
    Backend Server
       |
       v
    Web Application

這些元件可能由不同軟體、不同版本或不同設定組成。

每一層都需要解析 HTTP 請求，理解請求從哪裡開始、在哪裡結束，以及下一個請求何時開始。

## 三、HTTP Request Smuggling 是什麼？

HTTP Request Smuggling（HTTP 請求走私）是一類 HTTP 去同步（Desynchronization）問題，常見於請求經過反向代理、負載平衡器或其他前端元件，再交給後端伺服器處理的架構。

核心條件是：**同一段 HTTP 資料，在前端和後端被解析成不同的請求邊界。**

例如：
- 前端認為某個請求已經結束；
- 後端卻認為資料還沒有結束，或把後續位元組當成另一個請求；
- 連線上的請求佇列因此失去同步。

這不是單純「HTTP 標頭寫錯」；真正要研究的是整條代理鏈中不同解析器的行為差異。

## 四、為什麼 Content-Length 和 Transfer-Encoding 值得研究？

HTTP/1.1 常見的訊息長度資訊包括：
- `Content-Length`：表示訊息主體的位元組長度；
- `Transfer-Encoding: chunked`：表示主體使用分塊傳輸編碼。

研究文章常用以下名稱描述前後端的解析差異：

| 分類 | 常見含義 |
|---|---|
| CL.TE | 前端按 Content-Length 判斷邊界，後端按 Transfer-Encoding 判斷 |
| TE.CL | 前端按 Transfer-Encoding 判斷，後端按 Content-Length 判斷 |
| TE.TE | 兩端都支援 Transfer-Encoding，但對混淆、重複或格式異常的標頭處理不同 |

這些標籤是分類方式，不是看到某個標頭就能直接判定漏洞。實際上還要檢查代理是否正規化標頭、是否拒絕歧義請求，以及 HTTP/2 到 HTTP/1.1 的協議轉換是否產生新的解析差異。

本課主要解釋經典 HTTP/1.1 CL/TE 類型；HTTP/2 downgrade 和其他新型 desync 技術屬於後續進階內容。

## 五、研究員如何思考和發現？

### 第一步：先畫出請求路徑

不要一開始就發送大量特殊請求。

先了解：
- 是否存在 CDN？
- 是否存在 WAF？
- 是否使用反向代理？
- 是否存在多個後端？
- 是否重用後端連線？
- HTTP/1.1 和 HTTP/2 是否在不同層之間轉換？

### 第二步：確認解析邊界

研究員要問：

1. 前端如何判斷請求結束？
2. 後端如何判斷請求結束？
3. 兩者是否使用相同的解析規則？
4. 是否拒絕含糊或互相衝突的訊息？
5. 代理是否會修改、刪除或重新產生 HTTP 標頭？

### 第三步：建立安全的檢測假設

不要先追求影響最大的利用方式。

先在自己控制的環境中確認：
- 兩層系統是否出現解析差異？
- 是否能穩定重現？
- 是否能排除網路延遲和應用程式本身的異常？
- 是否會影響其他連線？

### 第四步：確認影響

只有在授權環境中，才進一步評估：
- 是否能造成請求錯配？
- 是否可能影響其他使用者請求？
- 是否可能繞過前端安全控制？
- 是否可能影響快取或後端路由？

如果測試可能影響其他使用者，就應停止擴大測試，改用隔離環境或供應商提供的測試方式。

## 六、為什麼這類漏洞容易被忽略？

因為每一層系統單獨看起來可能都正常。

例如：
- WAF 正常接受請求。
- 反向代理正常轉發資料。
- 後端伺服器正常解析資料。
- 但三者對訊息結束位置的理解不一致。

這種問題不是簡單的「某個輸入欄位沒有過濾」，而是多個元件之間的協議語義不一致。

這也是為什麼網路安全研究需要理解協定和架構，而不只是記住工具。

## 九、修復與防禦

開發和維運人員可以從以下方向降低風險：

1. 前端和後端使用一致且受支援的 HTTP 解析實作。
2. 拒絕有歧義或互相衝突的訊息長度標示。
3. 代理在轉發前正規化請求，避免不同元件重新解讀不一致的資料。
4. 定期更新 CDN、WAF、反向代理和後端伺服器。
5. 減少不必要的後端連線重用，並依供應商建議配置協議轉換。
6. 在部署前以整條代理鏈進行端到端測試。

不能只更新其中一台伺服器，就假設整條鏈路已經安全。

## 十、延伸案例：Web Cache Poisoning

另一篇非常值得閱讀的文章：

[Practical Web Cache Poisoning — PortSwigger Research](https://portswigger.net/research/practical-web-cache-poisoning)

研究員先找出會影響回應、但沒有被納入快取鍵（Cache Key）的輸入，再確認回應是否會被快取，最後評估影響。

可以從中學習另一種研究思路：

- 找出輸入。
- 觀察輸入是否影響輸出。
- 理解中間層如何保存結果。
- 判斷其他使用者是否可能收到錯誤的快取內容。
- 在不影響真實使用者的前提下證明問題。
