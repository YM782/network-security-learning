# 03-05｜真實漏洞研究案例：Dirty Pipe（CVE-2022-0847）

> 難度：初級至中級｜建議時間：120–150 分鐘｜先修：Linux 檔案、權限、程序、管線和系統資源
>
> 這是非常值得初學者反覆閱讀的真實漏洞發現故事。它從一張檔案損壞的客服工單開始，最後追查到 Linux 核心的記憶體與管線處理錯誤。

## 一、先讀原始研究文章

[The Dirty Pipe Vulnerability — Max Kellermann](https://dirtypipe.cm4all.com/)

CVE-2022-0847 是 Linux Kernel 的漏洞。它與 pipe buffer 的旗標初始化和 page cache 資料處理有關，在受影響條件下，可能讓沒有檔案寫入權限的本機程序改動唯讀檔案在頁面快取中的內容，造成嚴重權限影響。

本課不提供利用系統檔案取得 root 的操作步驟。重點是還原研究員怎麼發現、怎麼排除錯誤假設、怎麼建立最小重現，以及如何定位根因。

## 二、真正的發現起點：一張客服工單

Max Kellermann 最初收到客戶回報：下載的網站存取日誌無法正常解壓縮，`gzip` 回報 CRC 錯誤。他起初以為夜間日誌切割程序中斷，手動修正 CRC 後便關閉工單。

幾個月後，同類問題再次出現。他比較多份損壞檔案，注意到：
- 檔案內容大致正確，錯誤集中在檔案尾端的 CRC 和長度欄位；
- 多份檔案出現完全相同的錯誤位元組，而不是隨機變化；
- 異常位元組以 `50 4b 01 02` 開頭，這正是 ZIP 中央目錄檔案標頭的開頭；
- 產生 ZIP 標頭的 Web 服務沒有這些日誌檔案的寫入權限，正常情況下不應該改動它們。

他進一步掃描整個磁碟，找到三個月內 37 個損壞檔案；問題集中在提供 HTTP 下載的主要日誌伺服器，待命伺服器沒有同樣現象。每月最後一天特別容易出現問題，因為下載流程會把當月最後一份日誌接在 ZIP 中央目錄標頭之前。

這些細節把「一般檔案損壞」變成了可追查的線索：**損壞資料不是隨機垃圾，而是另一個程序原本要送到管線中的 ZIP 標頭。**

## 三、研究員如何逐步排除假設？

### 假設 A：硬碟或 RAM 故障

如果是硬體故障，資料損壞通常不會如此穩定地呈現相同結構。

研究員統計整個硬碟中的損壞檔案，發現損壞集中在特定伺服器，並且在每個月最後一天特別多。

這讓「隨機硬體故障」的解釋變得不合理。

### 假設 B：日誌切割程式寫錯

研究員重新閱讀服務架構，發現系統會使用 Linux 的 splice() 在檔案、管線和網路連線之間傳送資料。

splice() 可以避免某些資料在使用者空間與核心空間之間反覆複製，因此常用於高效能資料傳輸。

但它也代表研究員必須理解核心如何管理資料頁面和引用關係。

### 假設 C：ZIP 產生器直接寫壞日誌

奇怪的是，ZIP 產生器沒有日誌檔案的寫入權限。

正常權限檢查下，它不應該直接修改這些檔案。

這時候研究員開始懷疑：問題可能不在應用程式，而在核心處理資料頁面的方式。

## 四、最關鍵的轉折：建立最小重現

研究員將複雜的日誌服務縮成兩個小型 C 程式：

- 第一個程序持續把 `AAAAA` 寫入檔案，模擬日誌切割程序。
- 第二個程序透過 `splice()` 把檔案資料送進 pipe，再把 `BBBBB` 寫入 pipe，模擬 ZIP 產生器。

結果，原本只寫入 pipe 的 `BBBBB` 竟出現在檔案內容中，即使第二個程序本身沒有該檔案的寫入權限。

這個最小重現有兩個價值：
1. 它排除了原本應用程式中大量不相關的程式碼；
2. 它證明異常可以在兩個簡化程序中重現，研究範圍因此從日誌應用程式縮小到 Linux 核心的 pipe / page cache 處理。

作者最初以為問題需要一個同時寫入檔案的程序，並依賴競爭時序。後來理解核心機制後，才發現漏洞並不需要那個原始的併發寫入條件；可影響的情況比最初想像更廣。

## 五、理解根因：pipe buffer、page cache 和未初始化旗標

這部分是本案例的技術核心。

### 1. Page Cache 是什麼？

Linux 使用 Page Cache 快取檔案資料，減少重複讀取儲存裝置的成本。

簡化流程：

    SSD 中的檔案資料
           |
           v
       Page Cache
           |
           v
    程式讀取或使用資料

Page Cache 由核心管理，並不是使用者可以任意寫入的普通應用程式緩衝區。

### 2. Pipe 是什麼？

Pipe（管線）是一種程序間通訊方式，讓一個程序寫入資料，另一個程序讀取資料。

例如：

    程序 A ---> Pipe ---> 程序 B

Linux 會透過 pipe buffer 管理管線中的資料。

### 3. splice() 做什麼？

splice() 可以在檔案、管線和其他支援的檔案描述符之間傳送資料，避免不必要的使用者空間複製。

在某些情況下，核心會讓 pipe buffer 引用 Page Cache 中的頁面，而不是複製整份資料。

### 4. 真正的錯誤在哪裡？

真正的缺陷是某些建立 `struct pipe_buffer` 的核心程式路徑沒有初始化 `flags` 成員。

要理解它，必須把兩段歷史放在一起看：

1. 2016 年加入的 pipe-backed iterator 路徑，已經存在未初始化 `pipe_buffer.flags` 的問題；當時尚未有會讓這個未初始化值產生安全後果的旗標語義。
2. Linux 5.8 的提交 `f6dd975583bd` 將 pipe buffer 的可合併判斷改為每個 buffer 的 `PIPE_BUF_FLAG_CAN_MERGE` 旗標。
3. 因為舊程式路徑沒有把 `flags` 清零，page-cache-backed buffer 可能帶著未預期的 `CAN_MERGE` 旗標。
4. 如果核心因此把後續 pipe 寫入當成可以附加到既有 buffer，就可能把資料寫進原本由 Page Cache 管理的檔案頁面，而不是新配置的匿名 pipe buffer。

這說明一個很重要的漏洞研究現象：**引入漏洞的程式碼不一定就是最初引入缺陷的程式碼。** 舊的初始化缺陷，在後續重構改變旗標用途後，才變成可觸發的安全問題。

另外，Page Cache 中的資料被改動，不代表核心一定會把該頁標記為 dirty 並寫回磁碟；原始研究指出，某些情況下這種修改可能在記憶體快取中短暫存在，重啟或快取回收後可能消失。這不會降低漏洞本身的嚴重性，但有助於理解為什麼研究員看到的是檔案內容異常，以及為什麼觀察結果可能受快取狀態影響。

## 六、如何定位引入問題的程式碼？

研究員先確認問題在某些核心版本中出現、在較舊版本中沒有出現，然後使用 git bisect 定位引入問題的提交。

git bisect 的基本思想：

1. 找一個已知正常的版本。
2. 找一個已知有問題的版本。
3. 在兩者之間選擇中間提交。
4. 測試這個版本是否有問題。
5. 根據結果縮小範圍。
6. 重複直到定位引入問題的提交。

這是一種二分搜尋式的版本定位方法。

研究員在這個案例中，從 Linux v4.19 到 v5.10 之間約 185,011 個提交中，透過約 17 次二分測試定位到相關提交。

這比逐一閱讀所有提交有效得多。

## 七、漏洞修補

Linux 核心修補的關鍵是正確初始化 pipe buffer 的 flags。

原始修補進入了多個穩定核心版本，包括：
- Linux 5.16.11
- Linux 5.15.25
- Linux 5.10.102

實際設備是否安全，仍要依發行版安全公告和 backport 修補情況判斷。不能只用一個上游版本號推斷所有發行版的安全狀態。

## 八、在自己的 Kali 上做安全的基礎檢查

以下操作只查看本機，不會觸發漏洞。

### 1. 查看核心版本

    uname -r
    uname -a

### 2. 查看發行版資訊

    cat /etc/os-release

### 3. 查看已安裝的核心套件

    dpkg -l 'linux-image*'

### 4. 檢查本機檔案完整性

建立測試檔案：

    mkdir -p ~/cyber-practice/dirty-pipe-study
    cd ~/cyber-practice/dirty-pipe-study
    printf 'This is a local test file.\n' > sample.txt

計算雜湊：

    sha256sum sample.txt

複製後再比較：

    cp sample.txt sample-copy.txt
    sha256sum sample.txt sample-copy.txt

相同內容應產生相同 SHA-256 雜湊值。

這個實驗只教你建立完整性基準，並不是 Dirty Pipe 的漏洞重現。

## 九、另一個值得閱讀的 Linux 真實案例：Baron Samedit

[CVE-2021-3156 — Qualys：Heap-Based Buffer Overflow in Sudo](https://blog.qualys.com/vulnerabilities-threat-research/2021/01/26/cve-2021-3156-heap-based-buffer-overflow-in-sudo-baron-samedit)

這個漏洞位於 sudo 的命令列參數處理流程，涉及堆積緩衝區溢位（Heap-Based Buffer Overflow）。

Qualys 的研究說明指出，問題在程式碼中存在多年，並在特定參數處理路徑下造成越界寫入，可能使本機低權限使用者取得 root 權限。

閱讀時請注意：
- 輸入參數如何被解析？
- 不同執行模式是否走不同程式碼路徑？
- 緩衝區大小如何計算？
- 輸入長度和實際寫入長度是否一致？
- 為什麼測試一般命令列情境可能沒有觸及問題？

不要在日常 Kali 或其他真實系統上執行舊版 sudo 的漏洞 PoC。

## 十、從 Dirty Pipe 學習的漏洞研究方法

| 研究階段 | 這個案例的具體行動 |
|---|---|
| 發現異常 | gzip CRC 錯誤 |
| 蒐集證據 | 比較損壞檔案和位元組模式 |
| 建立假設 | 懷疑程式、權限、核心或硬體 |
| 排除假設 | 比較不同伺服器和發生時間 |
| 最小重現 | 簡化成兩個 C 程式 |
| 定位根因 | 分析 splice、pipe buffer 和 Page Cache |
| 版本定位 | 使用 git bisect |
| 修補 | 初始化未設定的旗標 |
| 負責任揭露 | 向核心安全團隊回報並協調修補 |
