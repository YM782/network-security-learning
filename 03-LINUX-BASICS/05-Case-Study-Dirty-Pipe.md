# 03-05｜真實漏洞研究案例：Dirty Pipe（CVE-2022-0847）

> 難度：初級至中級｜建議時間：120–150 分鐘｜先修：Linux 檔案、權限、程序、管線和系統資源
>
> 這是非常值得初學者反覆閱讀的真實漏洞發現故事。它從一張檔案損壞的客服工單開始，最後追查到 Linux 核心的記憶體與管線處理錯誤。

## 一、先讀原始研究文章

[The Dirty Pipe Vulnerability — Max Kellermann](https://dirtypipe.cm4all.com/)

CVE-2022-0847 是 Linux Kernel 的漏洞。它與 pipe buffer 的旗標初始化和 page cache 資料處理有關，在受影響條件下，可能讓沒有檔案寫入權限的本機程序改動唯讀檔案在頁面快取中的內容，造成嚴重權限影響。

本課不提供利用系統檔案取得 root 的操作步驟。重點是還原研究員怎麼發現、怎麼排除錯誤假設、怎麼建立最小重現，以及如何定位根因。

## 二、真正的發現起點：一張客服工單

Max Kellermann 最初收到客戶回報：下載的存取日誌無法正常解壓縮，gzip 顯示 CRC 錯誤。

第一次，他懷疑夜間日誌切割工作中途失敗，修正檔案後關閉工單。

但後來同樣問題反覆出現。研究員開始比較多份損壞檔案，發現一個不尋常的現象：

- 檔案內容大致正確。
- CRC 和長度欄位錯誤。
- 多份檔案出現相同的異常位元組。
- 異常位元組竟然像 ZIP 中央目錄標頭的開頭。
- 寫入 ZIP 標頭的服務理論上沒有這些日誌檔案的寫入權限。

這些不是普通的錯誤訊息，而是可以追查的證據。

## 三、研究員如何逐步排除假設？

### 假設 A：硬碟或 RAM 故障

如果是硬體故障，資料損壞通常不會如此穩定地呈現相同結構。

研究員統計整個硬碟中的損壞檔案，發現損壞集中在特定伺服器，並且在每個月最後一天特別多。

這讓「隨機硬體故障」的解釋變得不合理。

### 假設 B：日誌切割程式寫錯

研究員重新閱讀服務架構，發現系統會使用 Linux 的 splice() 在檔案、管線和網路連線之間傳送資料。

splice() 可以避免某些資料在使用者空間與核心空間之間反覆複製，因此常用於高效能資料傳輸。

但它也代表研究員必須理解核心如何管理資料頁面和引用關係。

### 假設 C：ZIP 產生器直接寫壞日誌

奇怪的是，ZIP 產生器沒有日誌檔案的寫入權限。

正常權限檢查下，它不應該直接修改這些檔案。

這時候研究員開始懷疑：問題可能不在應用程式，而在核心處理資料頁面的方式。

## 四、最關鍵的轉折：建立最小重現

研究員寫了兩個簡化的 C 程式：

- 一個模擬持續寫入檔案的日誌切割工作。
- 另一個模擬透過 splice() 傳送檔案資料，再向管線寫入另一段資料。

在測試中，第二個程序寫入管線的資料竟然出現在原本沒有寫入權限的檔案內容中。

這是非常重要的研究步驟：

**把一個複雜系統縮小成最少的元件，讓異常能夠穩定重現。**

最小重現（Minimal Reproducer）可以幫助研究員判斷問題究竟來自應用程式、函式庫、作業系統還是硬體。

## 五、理解根因：pipe buffer、page cache 和未初始化旗標

這部分是本案例的技術核心。

### 1. Page Cache 是什麼？

Linux 使用 Page Cache 快取檔案資料，減少重複讀取儲存裝置的成本。

簡化流程：

    SSD 中的檔案資料
           |
           v
       Page Cache
           |
           v
    程式讀取或使用資料

Page Cache 由核心管理，並不是使用者可以任意寫入的普通應用程式緩衝區。

### 2. Pipe 是什麼？

Pipe（管線）是一種程序間通訊方式，讓一個程序寫入資料，另一個程序讀取資料。

例如：

    程序 A ---> Pipe ---> 程序 B

Linux 會透過 pipe buffer 管理管線中的資料。

### 3. splice() 做什麼？

splice() 可以在檔案、管線和其他支援的檔案描述符之間傳送資料，避免不必要的使用者空間複製。

在某些情況下，核心會讓 pipe buffer 引用 Page Cache 中的頁面，而不是複製整份資料。

### 4. 真正的錯誤在哪裡？

研究員發現，某些建立 pipe buffer 的程式路徑沒有初始化 flags 成員。

早期這個問題沒有產生明顯後果；後來核心重構改變了判斷 buffer 是否可以合併資料的方式，讓這個未初始化旗標開始影響實際行為。

換句話說：

- 原本就存在的初始化缺陷。
- 後來程式碼修改了旗標的用途。
- 兩者組合後，讓錯誤變成可觸發的安全漏洞。

這種情況說明，單獨看一個程式碼變更可能看不出風險，必須理解它和既有資料結構、舊有程式路徑的互動。

## 六、如何定位引入問題的程式碼？

研究員先確認問題在某些核心版本中出現、在較舊版本中沒有出現，然後使用 git bisect 定位引入問題的提交。

git bisect 的基本思想：

1. 找一個已知正常的版本。
2. 找一個已知有問題的版本。
3. 在兩者之間選擇中間提交。
4. 測試這個版本是否有問題。
5. 根據結果縮小範圍。
6. 重複直到定位引入問題的提交。

這是一種二分搜尋式的版本定位方法。

研究員在這個案例中，從超過 18 萬個提交中，透過 17 次左右的測試定位到相關提交。

這比逐一閱讀所有提交有效得多。

## 七、漏洞修補

Linux 核心修補的關鍵是正確初始化 pipe buffer 的 flags。

原始修補進入了多個穩定核心版本，包括：
- Linux 5.16.11
- Linux 5.15.25
- Linux 5.10.102

實際設備是否安全，仍要依發行版安全公告和 backport 修補情況判斷。不能只用一個上游版本號推斷所有發行版的安全狀態。

## 八、在自己的 Kali 上做安全的基礎檢查

以下操作只查看本機，不會觸發漏洞。

### 1. 查看核心版本

    uname -r
    uname -a

### 2. 查看發行版資訊

    cat /etc/os-release

### 3. 查看已安裝的核心套件

    dpkg -l 'linux-image*'

### 4. 檢查本機檔案完整性

建立測試檔案：

    mkdir -p ~/cyber-practice/dirty-pipe-study
    cd ~/cyber-practice/dirty-pipe-study
    printf 'This is a local test file.\n' > sample.txt

計算雜湊：

    sha256sum sample.txt

複製後再比較：

    cp sample.txt sample-copy.txt
    sha256sum sample.txt sample-copy.txt

相同內容應產生相同 SHA-256 雜湊值。

這個實驗只教你建立完整性基準，並不是 Dirty Pipe 的漏洞重現。

## 九、另一個值得閱讀的 Linux 真實案例：Baron Samedit

[CVE-2021-3156 — Qualys：Heap-Based Buffer Overflow in Sudo](https://blog.qualys.com/vulnerabilities-threat-research/2021/01/26/cve-2021-3156-heap-based-buffer-overflow-in-sudo-baron-samedit)

這個漏洞位於 sudo 的命令列參數處理流程，涉及堆積緩衝區溢位（Heap-Based Buffer Overflow）。

Qualys 的研究說明指出，問題在程式碼中存在多年，並在特定參數處理路徑下造成越界寫入，可能使本機低權限使用者取得 root 權限。

閱讀時請注意：
- 輸入參數如何被解析？
- 不同執行模式是否走不同程式碼路徑？
- 緩衝區大小如何計算？
- 輸入長度和實際寫入長度是否一致？
- 為什麼測試一般命令列情境可能沒有觸及問題？

不要在日常 Kali 或其他真實系統上執行舊版 sudo 的漏洞 PoC。

## 十、從 Dirty Pipe 學習的漏洞研究方法

| 研究階段 | 這個案例的具體行動 |
|---|---|
| 發現異常 | gzip CRC 錯誤 |
| 蒐集證據 | 比較損壞檔案和位元組模式 |
| 建立假設 | 懷疑程式、權限、核心或硬體 |
| 排除假設 | 比較不同伺服器和發生時間 |
| 最小重現 | 簡化成兩個 C 程式 |
| 定位根因 | 分析 splice、pipe buffer 和 Page Cache |
| 版本定位 | 使用 git bisect |
| 修補 | 初始化未設定的旗標 |
| 負責任揭露 | 向核心安全團隊回報並協調修補 |
